# Top-Down Learning — Aptuni Flagship Plugin #1

> Learn only what you need, from what you already know, to reach where you want to go.
>
> 从你已经会的地方出发，只学习抵达目标真正需要的知识。

Traditional learning goes field → foundations → curriculum → eventually the target. Top-Down
Learning starts at the target, finds what this learner already knows, and teaches only the missing
prerequisites, just in time, returning to the target after each one. Top-down does not mean
skipping foundations. It means just-in-time foundations instead of every possible foundation in
advance.

Top-Down Learning is the first serious consumer of Aptuni as a personal context platform for Agent
plugins. It imports only `aptuni.api.v1`; Aptuni Core contains no learning logic.

## The first run

```text
/top-down-learning:top-down-study        (Claude Code)
$top-down-study                          (Codex)
"I want to learn Transformers."
```

1. **Target.** The Agent asks about depth, deliverable or time only when the answer changes the
   path.
2. **Relevant context.** The plugin runs task-scoped queries for each proposed prerequisite and
   for learning preferences. Only concept labels, an inferred level and learning-relevant preference
   lines reach the draft. The full Profile, raw Memory, canonical identifiers and provenance never
   do. No separate `@aptuni profile` activation is needed.
3. **Targeted questions.** At most three questions, and only ones whose answers would change the
   path.
4. **Verification.** The Agent summarizes the target, foundation, preferences and proposed path,
   then asks: *is this accurate, and what should be corrected or added?* Teaching starts only after
   an explicit yes.
5. **Local or cloud.** Continue here, or export a portable context for a cloud or other Agent.
   Neither is better in general.

## The portable learning context

Every step reads and returns `top_down_learning_context.md`, schema
`aptuni.top-down-learning.context@1` ([ADR-0026](../../../docs/dev/DECISIONS/ADR-0026-top-down-portable-learning-context.md)).
It is the continuity layer of the learning experience, not an incidental log. It keeps what you are
trying to achieve, what you already know, how you learn well, what has been verified, where you are
and what comes next. It is human-readable, Agent-readable and usable without Aptuni.

- **Stable state** covers the target, success criteria, depth and deliverable, foundation,
  learning preferences and constraints. Verification is bound to a digest of these fields, so any
  change requires verifying again.
- **Dynamic state** covers diagnostics, the prerequisite map, path, strategy, position,
  demonstrations, misconceptions, gaps and next step. It changes as you learn and never becomes
  Profile information on its own.
- **Personalized Teaching Strategy** is written by the teaching Agent for this learner and
  platform. The plugin supplies principles and preference-derived affordances in the
  **Teaching Contract**, for example diagrams for a visual learner or why → mechanism →
  implementation for a first-principles learner. It does not hard-code one method.
- **Cloud Teaching Guidance** tells another Agent how to continue from the current position,
  respect verified foundation, require learner output and return a refreshed checkpoint.

Examples generated by the real workflow for a synthetic learner are in
[`examples/transformer_local_context.md`](examples/transformer_local_context.md) and
[`examples/transformer_cloud_context.md`](examples/transformer_cloud_context.md). Regenerate them
with `tools/regenerate_top_down_demo.py`.

## Local teaching

The local Agent writes the returned Markdown to `./top_down_learning_context.md` after each step.
It can run code, generate diagrams or small HTML visualizations and connect lessons to your project.
It picks the smallest useful mix of explain, visualize, predict, apply, retrieval practice and
explain-back. You must produce output before progress is recorded. The Agent diagnoses each output
as understood, partial, misconception or unknown, and then advances, reinforces, descends into one
missing prerequisite, or returns from it once understood. For example, Transformer → self-attention →
unclear why a query-key dot product measures relevance → a brief geometric dot product → verified →
straight back to self-attention.

## Cloud or another Agent

`top_down_export_cloud`, or choosing cloud delivery, returns a self-contained copy. It is refused
until the context is verified. It never calls Aptuni and cannot widen the grant. Path-, email-,
credential- and token-shaped text is redacted from dynamic sections. If such text appears in
verified stable sections, the export is refused so that you can correct it. Paste the file into any
capable Agent. After meaningful progress, ask it for a refreshed checkpoint, and bring that back to
a local Agent with `top_down_resume`. Dynamic updates keep verification. Edits to stable sections
require verifying again.

## Memory boundary

Nothing is written to Aptuni during learning. `top_down_propose_memory` runs only when you ask. It
creates a quarantined proposal for owner review. A demonstrated-understanding proposal needs at
least two recorded demonstrations, because one successful exercise is not stable competence. The
optional `memory.propose` capability fails closed when it is withheld.

## Install and authorize

The easiest path is to ask your Agent to run `aptuni guide agent` and say you want Top-Down
Learning: it installs the plugin, adds its grant to the same setup plan, and you type one APPLY.

By hand, with the published Beta (`aptuni` from PyPI, the plugin from the exact release tag):

```sh
uv tool install aptuni==0.2.0b2
uv tool install "git+https://github.com/ruihaomei/aptuni@v0.2.0b2#subdirectory=examples/plugins/top_down_learning"
aptuni developer grant plan "$(top-down-study-mcp --manifest-path)"
aptuni developer grant apply ACTION_ID        # read the consent screen, then type APPLY
```

The plugin finds its own grant: it uses the newest owner grant bound to its exact manifest digest
(`aptuni developer grant list`). Set `APTUNI_TOP_DOWN_GRANT_ID` only to pin a specific grant. The
plugin wheel and sdist are also attached to the GitHub Release with their SHA-256 sums. Each
`uv tool` environment carries its own copy of `aptuni`, so upgrade both tools together.

The plan grants the required `context.read` and, by default, the optional `memory.propose`. To
withhold memory capture, add `--capability context.read` to `grant plan`. A new plugin version
changes the manifest, so plan its grant again after upgrading.

**Claude Code:**

```sh
claude plugin marketplace add ruihaomei/aptuni
claude plugin install top-down-learning@aptuni
```

Start a new session and invoke `/top-down-learning:top-down-study`. The skill is user-only and has
no automatic hook. (For one session only: `claude --plugin-dir PATH/examples/plugins/top_down_learning/claude`.)

**Codex:**

```sh
codex plugin marketplace add ruihaomei/aptuni
codex plugin add top-down-learning@aptuni
```

Start a new session and invoke `$top-down-study`. Implicit invocation is disabled. Add
`APTUNI_STATE_DIR` to the server environment only if you use a non-default state directory.

## Boundaries and limits

- Both hosts call the same eight no-egress STDIO tools. The server is stateless: the context text
  goes in and comes back out.
- Revoking the grant stops the next Aptuni-backed call (`top_down_prepare`,
  `top_down_propose_memory`). File-only tools keep working on your own portable file, because they
  read nothing from Aptuni.
- Verification prevents skipped, stale or hand-flipped confirmation. As with ADR-0025, a
  model-mediated host cannot prove that a human typed the confirmation, and a determined local Agent
  could rewrite your file. Verification protects workflow integrity. It is not authentication.
- Learner replies and confirmations are checked and then discarded. Only the Agent's short
  summaries are stored.
- The inferred level for an Agent-chosen evidence term reveals whether matching knowledge/skills
  records exist. The query count is bounded (at most 36 terms per draft) and scoped to the plugin's
  grant; that is the price of task-relevant personalization.
